# The data regions of the SX-KN6000 and SX-KN6500 program flash, as typed source

Lane sib-kn6000 of the data-semantics effort (`notes/data-semantics-2026-10-29/README.md` at the
repository root), 2026-10-29.  Until this lane the data between the application's code and the
MILK kernel was 23 (KN6000) / 24 (KN6500) `.incbin_range` lines, and 300 / 303 more cut the code.
Both images now take their data region from `src/program/data/`, generated by
`../kn7000/tools/gen_data_s.py --profile kn6000|kn6500`, and stay byte-identical (`make verify`).
The description is the KN7000's (lane gui-kn7000, `../../kn7000/notes/gui-data-region/README.md`):
the same tools, given a profile, not copied.

| model   | data region (file)    | CPU                   | RAM-init image (ROM -> RAM)          |
|---------|-----------------------|-----------------------|--------------------------------------|
| KN6000  | `0x176037..0x3F47EC`  | `0x4C176037..`        | `0x4C3ED870 -> 0x50000010`, `0x6F7C` |
| KN6500  | `0x176839..0x37E44C`  | `0x4C176839..`        | read from its crt0 the same way      |

## The MILK object system of these firmwares

### The registry: the KN5000's layout, not the KN7000's

`RegisterObjectTable` (KN6000 v7.1 CPU `0x4C01D198`) copies the 16-byte `{class, proc, u16 count,
u16 pad, table}` record to `0x5024BE58 + 16 * slot`, slot <= `0x35F`.  The tables are grouped by
KIND, as in the KN5000's NAKA (`scripts/analysis/nakarest_objtab_map.py`), not by block as on the
KN7000 (`milk_model.SCHEMES["naka"]`):

| slots              | kind                               | registered by                     |
|--------------------|------------------------------------|-----------------------------------|
| `0x000 + V`        | Viewable (one per screen group)    | InitializeUserNN                  |
| `0x100 + N`        | Function                           | InitializeUserNN, module N        |
| `0x120 + N`        | ApFunction                         |                                   |
| `0x140 + N`        | MainFunction                       |                                   |
| `0x160 + N`        | Class                              |                                   |
| `0x180 + N`        | ResEvent                           |                                   |
| `0x1A0 + N`        | ResMethod                          |                                   |
| `0x1C0`            | SupportClass                       | InitSptClassTable                 |
| `0x1E0`, `0x1F0`   | Mode, Title                        | InitModeTitleTable                |
| `0x200 + V`        | ResName, parallel to Viewable V    |                                   |
| `0x300 + N` ...    | the names of the three function tables |                               |

The kind of a registration is the name of the class its record carries: `0x0160000K` is entry K of
the root class table at slot `0x160`, found as the registration whose class id names its own slot
(slot 4 on the KN7000).  An id is `(slot << 16) | index` as on the KN7000.  The class tables'
counts are halfwords beside the tables (`movhu (ADDR), d0`); the register tracker reads them from
the image.  `InitializeObjectTable` first registers every slot empty (table 0): skipped.  11
modules register tables (InitializeUser00 .. 18; the others are empty stubs).

### The type characters

The class records are the KN7000's (proc, parent, allsize, selfsize, name, propdata, propname) and
the field layout is the same aligned C struct layout.  The propdata alphabet differs: the older
firmware has no `\`, so its `]` `^` `_` are the KN7000's `\` `]` `^` (flag, colour, border), and
its `m`..`w` are the KN7000's `l`..`v`.  `notes/data-region-probes/sigmap.py` pairs the fields of
every same-named class of KN6000 v7.1 and KN7000 941: 591 pairs, one KN7000 character per KN6000
character (`milk_model.SIGMAP_NAKA`).  With the translation, selfsize and allsize hold for all 449
(KN6000) / 451 (KN6500) classes and every super / sub / next / prev link checks, as on the KN7000.
Only `l` (the `user` field of Mode and Title, no widget record) has no twin.

### Widget records, ids and names

Everything in `../../kn7000/notes/gui-data-region/README.md` ("Widget records", "Object names")
applies: one macro per class, the record's links as object names, its tree as indentation, rect as
X / Y / W / H, CL_ / BD_ / ES_ / VF_ names from `src/constants.inc` (the firmware's own name /
value tables, `gen_constants.py --base 0x4C000000 --scan 0x180000:0x1A0000`), TT_ / MD_ / FN_ ids
by name.  A Viewable table is named `V_<its first root object's ResName>` (the KN6000 has no OT
blocks: no RegisterOTBlock), a module's tables `UserNN` after the routine that registers them.

The code names ids too: `cmp MT_GetBitmapData, d1`, `mov CLASS_Class, d0`, `mov FN_..., d1`,
`<object>_id` (`gui_code_ids.inc`; table 0's object ids are below `0x10000` and stay numbers).

`functions.sym` gives the code the firmware's own name of each procedure a MILK Function /
ApFunction / MainFunction table lists (the parallel name table), where no other symbol file names
it: 551 names on the KN6000.  `gen_symbols.py` had found only 21 of these tables.

## Other typed structures

| structure                       | KN6000 / KN6500                  | evidence                                                         |
|---------------------------------|----------------------------------|------------------------------------------------------------------|
| demo songs (36 zlib streams)    | both: 12 songs x record / events / panel bank | `kn_sqt.py` (song record 0x870 B on the KN6000) / `kn_panel.py`; `.zlib 6` re-compresses byte-exactly |
| `TechnicsRhythmsResource`       | `0x4C359AC0` / `0x4C2E5304`      | IC18's format, one style " 8 Beat 1" (`program_rhythm.py`); func_4C0557E9 falls back to it when the table ROM's resource does not check |
| bitmap resources (13 / 13)      | both                             | procedures answering MT_GetBitmapData / Width / Height / Palette / GetBitCount (`gen_data_s.py bitmaps()`); PNG, `table_png.py pk D W H` |
| `ToneRecordDirectory`           | KN6000 `0x4C3E5FD4` (2,475 entries) | func_4C07C26A: record index -> address when no archive is loaded; tone records (SOUND_HEAD + n SOUND_MOD), TABLE tones, voice records (`voice_record.inc`) |
| `FactoryPanelMemory`            | KN6000 `0x4C32BE24`, 13 banks x 8 | func_4C03D431 copies it (0x2D8D0 bytes) and the .PMT header to the backup RAM `0x840007C2`: the factory reset; PMR_ lines |
| JPEG / BMP files                | 3                                | whole files                                                      |

The bitmap PNGs keep the pixel VALUES; their palette is the bitmap's own when it has one, grey
levels otherwise.  The pixel order is the drawing code's (traced 2026-11-02, lane mn10300-names; it was an
[INFERENCE] from the pictures): `VwUserBitmapProc` (0x4C00AA38), the MT_GetBitmapData consumer, asks
MT_GetBitCount and draws 1 bit with `DrawBitmapSP2`, 8 bits with `DrawBitmapSPFast256` / `DrawBitmapSPFast`, any
other depth (4) with `DrawBitmapSPFast16`.  `DrawBitmapSP2_Impl` reads each row as 16-bit words, swaps the two
bytes (`asr 8, d2 / and 0xff, d2 ... asl 8, d1 / add d1, d2`) and tests bit 15 - n for pixel n, so the leftmost
pixel is bit 7 of the first byte, a set bit is the foreground colour; rows are whole 16-bit words.
`DrawBitmapSPFast16_Impl` expands each byte through `DrawBitmapSPFast16_Impl_entry_L58_Table`, whose entry b is
(0x20 + (b & 0xF)) << 8 | (0x20 + (b >> 4)), and stores the low byte first, so the high nibble is the left
pixel, drawn as colour 0x20 + n; it loads palette entries 0x20..0x2F from the bitmap's 16 colours and skips a
byte after an odd row byte count.  `DrawBitmapSPFast256_Impl` copies a row as is (`memcpy`) and steps
(w + 1) / 2 * 2 bytes.  So every row pad is to an even byte count, as the room up to the next referenced
address also shows.

## Website page draft

(For `kn6000-program-data.md` in technics-docs, to be added by the website sync.)

> **The SX-KN6000's and SX-KN6500's screens and built-in data in the source.**  Like the KN7000,
> these firmwares draw every screen from MILK widget records: 7,145 (KN6000 v7.1) and 7,203
> (KN6500 v1.3), each an instance of one of 449 / 451 self-describing classes.  The disassembly
> writes each record as one line named by its class, nested under its parent, with its links,
> colours, borders, titles and procedures by name; `notes/gui-menu-map.md` lists every screen.
> The registry is the KN5000's (tables grouped by kind, ids `(slot << 16) | index`), and the
> field-type alphabet is the KN7000's shifted by one.  The program flash also carries a fallback
> "Technics Rhythms" style (one style, the IC18 format), twelve demo songs (zlib, typed event by
> event), thirteen bitmaps (PNG), and on the KN6000 its 2,473 built-in tone and voice records and
> the 104 factory panel memories.
