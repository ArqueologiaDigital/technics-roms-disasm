# Technics SX-KN6500 program flash (update v1.3)

A byte-exact disassembly of the program flash image of the Technics SX-KN6500 arranger. The CPU
is a Panasonic MN10300 running the MILK framework, as in the SX-KN7000 (`../kn7000/`) and the
SX-KN2400 (`../kn2400/`). The assembler and every helper script come from the KN7000 tree, used
by relative path (`../kn7000/tools`); nothing is copied.

The SX-KN6000 (`../kn6000/`) has the same layout, and its tree is made the same way.

    make            # regenerate baserom/ if needed, assemble, compare: must print OK

`make` needs the Technics customer-service mirror beside this repository
(`../../ca-software-mirror/files`, private). Point `CA_MIRROR=` at it if it lives elsewhere.
The build needs only Python 3. `make program-src` also needs MAME's `unidasm`
(`UNIDASM=`, default `../../tools/unidasm`).

## What is not here: the table ROMs IC13 / IC14

The SX-KN6500's two 16 Mbit table-data ROMs, IC13 and IC14 (`C3FBMD000069` / `C3FBMD000068`), are **undumped**.
They hold the built-in style and sound tables. The update floppies do not carry them,
because only the program flash can be updated in the field. The only image that exists is
the placeholder the MAME driver generates (`kn6500_table_fontph.rom`). This tree reproduces the
program flash (IC11 / IC12) only.

## The reference image (not in git)

The image is copyrighted, so `baserom/` is git-ignored. `make baserom` rebuilds it from the
manufacturer's update, without running any of its programs:

| outer archive   | `sfx_extract.py kn65-13.zip`       | `kn65_v1-3a.exe`, `kn65_v1-3b.exe` (self-extracting ZIPs) |

## Layout

The whole image is linked for `0x4C000000`. The firmware runs its program from there, and the
MAME driver copies the program flash into that window; the documentation site's
`kn6000-hardware` page has the details.

| file offsets          | contents                                                                   |
|-----------------------|----------------------------------------------------------------------------|
| `0x000000`-`0x000010` | boot header: `_reset` (jmp to `crt0_start`), 5 nops, `_vector_08`, 3 bytes |
| `0x000010`-`0x000080` | erased (0xFF)                                                              |
| `0x000080`-`0x176839` | code: start-up, the application, the C runtime                             |
| `0x176839`-`0x37e44c` | data                                                                       |
| `0x37e44c`-`0x381447` | code: the MILK kernel (uITRON services `del_mbx` ... `dly_tsk`)            |
| `0x381447`-`0x381691` | data, including the `MILK MN10300 Ver1.0R1` banner at `0x381448`           |

The code ranges are the ones `src/program.s` was generated with (Makefile `CODE`). Their ends
are where the reached code stops: past them, no traced path enters and no named entry lies.

## Symbols

- `kn6500.sym` / `src/symbols.inc` (generated by `make symbols`) hold 1,395 function names.
  They come from the firmware's own MILK reflection tables, found by
  `../kn7000/tools/gen_symbols.py`. Only tables whose procedures land in the code ranges count.
  With the whole image counted as code, the tool also accepts a `DiskMenu` table of 40
  entries whose pointers lead into data, and would name 39 more addresses wrongly (one entry is
  a null pointer). `../kn7000/notes/sibling-symbol-probes/whole_image_pairings.py` produces
  these figures; its README has the command and the output.
- `kn6500_manual.sym` holds names recovered by hand: `_reset`, `_vector_08`, `crt0_start`.
- `kn6500_ported.sym` (`make ported-names`, generated) holds 722 names carried over from the
  KN7000 (program 941). `../kn7000/tools/port_names_by_code.py` carries a name when one of
  this image's unnamed entries is the same code as a routine the KN7000's symbol files name:
  the same instructions from the entry to the first return, with every number of 0x10000 or
  more masked out (addresses, and MILK message codes, which are renumbered between models).
  At least 8 of those instructions must have nothing masked, and the match must be unique among
  all of the KN7000's routine starts (every `movm` prologue and call target, named or not) and
  among this image's entries. Each row records the KN7000 address it came from; the file's
  header counts what was not carried.
  `--fuzzy` then compares whole routine bodies on what is left
  (`../kn7000/tools/fn_similarity.py`: every instruction control flow reaches, small
  immediates allowed to differ, callees and referenced strings compared by name, the two
  routines each other's best match). It carried 76 of the 722; their rows say "whole body"
  and give the match class and the two similarity ratios.
- `src/program/data/functions.sym` (generated by `make data-src`) holds the procedures the MILK
  Function / ApFunction / MainFunction tables name in their parallel name tables, where no file
  above names the address: 427 names. `gen_symbols.py` finds only the reflection tables whose
  procedures it can pair; these tables are the ones the InitializeUserNN routines register
  (`../kn6000/notes/data-region.md`).
- `src/labels.inc` is generated with the source. It holds every other label the source defines:
  `func_<ADDR>` for an entry no table names, `<name>_entry` for a register-save `call` entry,
  and `<entry>_L<offset>` for a branch target. `../kn2400/README.md` explains these
  conventions.

## The source

`src/program.s` is generated by `make program-src`, which runs `../kn7000/tools/gen_image_s.py`.
The generator's header describes the method. Only code that a traced path reaches becomes
instructions, re-encoded by `mn10300_asm` and compared with the image; with `--decode-gaps`
the code-range bytes no traced path reaches are decoded too, run by run. The data region is
typed source in `src/program/data/` (see "The data"), included in place of its bytes. The
figures come from `notes/conversion-stats.txt`, which the generator writes:

`named` counts the independent names (the reflection-table, manual and ported files);
`derived` counts the `<name>_entry` register-save labels of named functions, which take their
name from the function. `python3 ../kn7000/tools/stats_table_md.py notes/conversion-stats.txt`
prints the table.

| measure                      | value                                                            |
|------------------------------|------------------------------------------------------------------|
| entries                      | 13,555 (2,547 named, 688 derived `<name>_entry`, 10,320 `func_`) |
| bytes emitted as code        | 1,533,085: 99.15% of the code-range bytes                        |
| instructions                 | 580,046, plus 88 `.byte` escapes                                 |
| local branch labels          | 46,578                                                           |
| code-range bytes left binary | 3, in 1 `.incbin_range` pieces                                   |

## The data

The data region between the application's code and the MILK kernel is `src/program/data/`,
generated by `../kn7000/tools/gen_data_s.py --profile kn6500` (`make data-and-code-src`, with
`make program-src`, to a fixpoint): the MILK class tables, every widget record as one macro line
nested under its parent (links, colours, titles and procedures by name), the event / method /
function / title tables, strings, the demo songs typed inside `.zlib` blocks, the built-in
"Technics Rhythms" style, the bitmap resources as PNG.
The code names data addresses by label and MILK ids by name. `notes/gui-menu-map.md` is the
generated menu map (`make gui-map`; `make verify-gui-map` checks it). Format, evidence, census
and what is still a blob: `../kn6000/notes/data-region.md`.
