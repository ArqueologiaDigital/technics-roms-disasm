# Technics SX-KN6500 program flash (update v1.3)

A byte-exact disassembly of the program flash image of the Technics SX-KN6500 arranger. The CPU
is a Panasonic MN10300 running the MILK framework, as in the SX-KN7000 (`../kn7000/`) and the
SX-KN2400 (`../kn2400/`). The assembler and every helper script come from the KN7000 tree, used
by relative path (`../kn7000/tools`); nothing is copied.

The SX-KN6000 (`../kn6000/`) has the same layout, and its tree is made the same way.

    make            # regenerate baserom/ if needed, assemble, compare: must print OK

`make` needs the Technics customer-service mirror beside this repository
(`../../ca-software-mirror/files`, private). Point `CA_MIRROR=` at it if it lives elsewhere.
The build needs only Python 3. `make program-src` also needs MAME's `unidasm`
(`UNIDASM=`, default `../../tools/unidasm`).

## What is not here: the table ROMs IC13 / IC14

The SX-KN6500's two 16 Mbit table-data ROMs, IC13 and IC14 (`C3FBMD000069` / `C3FBMD000068`), are **undumped**.
They hold the built-in style and sound tables. The update floppies do not carry them,
because only the program flash can be updated in the field. The only image that exists is
the placeholder the MAME driver generates (`kn6500_table_fontph.rom`). This tree reproduces the
program flash (IC11 / IC12) only.

## The reference image (not in git)

The image is copyrighted, so `baserom/` is git-ignored. `make baserom` rebuilds it from the
manufacturer's update, without running any of its programs:

| step            | tool                               | result                                                    |
|-----------------|------------------------------------|-----------------------------------------------------------|
| outer archive   | `sfx_extract.py kn65-13.zip`       | `kn65_v1-3a.exe`, `kn65_v1-3b.exe` (self-extracting ZIPs) |
| floppy contents | `sfx_extract.py`                   | `IKV1.SLD`, `IKV2.SLD`, `SMCKPV1.INF`                     |
| decompression   | `sld_decompress.py`                | 0x200000 + 0x181691 bytes                                 |
| join            | `cat`                              | `kn6500_program.rom`, 3,675,793 bytes                     |
| checksum file   | `smck_check.py ... --expect match` | total 0x157ED142, 15/15 block sums match                  |
| recorded SHA-1  | Makefile `ROM_SHA1`                | `a507de3977def5d4148c4d3dbc16e3f6ff9f01c8`                |

## Layout

The whole image is linked for `0x4C000000`. The firmware runs its program from there, and the
MAME driver copies the program flash into that window; the documentation site's
`kn6000-hardware` page has the details.

| file offsets          | contents                                                                   |
|-----------------------|----------------------------------------------------------------------------|
| `0x000000`-`0x000010` | boot header: `_reset` (jmp to `crt0_start`), 5 nops, `_vector_08`, 3 bytes |
| `0x000010`-`0x000080` | erased (0xFF)                                                              |
| `0x000080`-`0x176839` | code: start-up, the application, the C runtime                             |
| `0x176839`-`0x37e44c` | data                                                                       |
| `0x37e44c`-`0x381447` | code: the MILK kernel (uITRON services `del_mbx` ... `dly_tsk`)            |
| `0x381447`-`0x381691` | data, including the `MILK MN10300 Ver1.0R1` banner at `0x381448`           |

The code ranges are the ones `src/program.s` was generated with (Makefile `CODE`). Their ends
are where the reached code stops: past them, no traced path enters and no named entry lies.

## Symbols

- `kn6500.sym` / `src/symbols.inc` (generated by `make symbols`) hold 1,395 function names.
  They come from the firmware's own MILK reflection tables, found by
  `../kn7000/tools/gen_symbols.py`. Only tables whose procedures land in the code ranges count.
  With the whole image counted as code, the tool also accepts a `DiskMenu` table of 39
  entries whose pointers lead into data, and those pairings are wrong.
- `kn6500_manual.sym` holds names recovered by hand: `_reset`, `_vector_08`, `crt0_start`.
- `kn6500_ported.sym` (`make ported-names`, generated) holds 572 names carried over from the
  KN7000 (program 941). `../kn7000/tools/port_names_by_code.py` carries a name when one of
  this image's unnamed entries is the same code as a routine the KN7000's symbol files name:
  the same instructions from the entry to the first return, with addresses masked out,
  at least 8 of them, and a unique match on both sides. Each row records the KN7000 address
  it came from.
- `src/labels.inc` is generated with the source. It holds every other label the source defines:
  `func_<ADDR>` for an entry no table names, `<name>_entry` for a register-save `call` entry,
  and `<entry>_L<offset>` for a branch target. `../kn2400/README.md` explains these
  conventions.

## The source

`src/program.s` is generated by `make program-src`, which runs `../kn7000/tools/gen_image_s.py`.
The generator's header describes the method. Only code that a traced path reaches becomes
instructions, re-encoded by `mn10300_asm` and compared with the image. Everything else stays
`.incbin_range` from `baserom/`. The figures come from `notes/conversion-stats.txt`, which the
generator writes:

| measure                      | value                                 |
|------------------------------|---------------------------------------|
| entries                      | 13,323 (2,529 named, 10,794 `func_`)  |
| bytes emitted as code        | 1,530,172: 98.96% of the code ranges  |
| instructions                 | 574,135, plus 285 `.byte` escapes     |
| local branch labels          | 43,667                                |
| code-range bytes left binary | 16,115, in 303 `.incbin_range` pieces |

## Open work

- Names: 10,794 entries are still `func_<ADDR>`. `make ported-names` carries only exact,
  unique matches from the KN7000. Routines that differ slightly need another method, and
  names from the KN2400's and the other KN6xxx's reflection tables have not been
  carried yet.
- RAM, I/O and data addresses are still numbers in the source.
- The data region is one `.incbin_range`. Nothing in it has been typed yet.
