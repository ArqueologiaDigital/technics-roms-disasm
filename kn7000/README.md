# KN7000 disassembly

A byte-exact disassembly project for the **Technics SX-KN7000** firmware.

The keyboard's main CPU is a **Panasonic MN10300/AM33** (it embeds the kernel
banner `MILK MN10300 Ver1.0R1`) — *not* the Toshiba TLCS-900 used by the KN5000.
The two flash images reverse-engineered here are produced by the sibling
[`kn7000_extraction`](../../kn7000_extraction) repo from the original system-update
floppy disks:

* `kn7000_program.rom` — 0x3F6F01 bytes, main firmware, mapped at CPU `0x48400000`
* `kn7000_table.rom` — 0x3E94D4 bytes, resource archive, mapped at CPU `0x48000000`

## Goal: 100% byte-match

`make verify` reassembles the source in `src/` and checks that the result is
**byte-for-byte identical** to the original images:

```
$ make verify
OK    kn7000_program.rom is 100% byte-identical to the original
OK    kn7000_table.rom is 100% byte-identical to the original

All images reproduced byte-for-byte.
```

The project is already at 100% match — because it *starts* as a skeleton in
which every byte is pulled in verbatim (`.incbin_range`). Reverse engineering
then proceeds by replacing those raw ranges, region by region, with real
disassembled instructions and typed data — while `make verify` guarantees the
rebuilt image never drifts from the original. "Understood" bytes go up; the
byte-match invariant is held at 100% the whole way.

## Symbols — reusing KN5000 knowledge

**2,302 functions are named for free**, recovered from the firmware's own runtime
reflection tables by [`tools/gen_symbols.py`](tools/gen_symbols.py). The KN7000
runs the same object-oriented "MILK" UI toolkit as the KN5000, and embeds **~114
index-parallel tables** — each a run of code pointers, a NUL, then a run of name
pointers — that its `MT_GetProcedure`-style lookup uses at runtime. The tool
discovers them all generically (a function-prologue check on the paired targets
rejects look-alike event-id / widget-id tables), recovering names like
`SleepMainTask`, `DispatchEvent`, and the whole `Ac*`/`Vw*`/`Ps*`/`Iv*`/`Tt*`
widget window-procedure set (518 `*Proc` + 353 `*Func` handlers) — the **same
names documented for the KN5000** (see the kn5000-docs *Shared Codebase Map*).
The code/name arrays are aligned **directly** (`code[k] ↔ name[k]`) — verified
behaviourally: under this pairing every `Get*` accessor reads its variable and
every `Set*` writes it, with no exceptions (the shifted pairing produced
impossible getters that write memory).

The names land in two places: `kn7000.sym` (a portable `0xADDR name` table) and
`src/symbols.inc` (`.equ` form, `.include`d by `src/program.s` so future
disassembled code can reference functions by name). `make disasm` also emits
`disasm/program_named.asm` — a named, function-by-function listing;
[`disasm/program_named_sample.asm`](disasm/program_named_sample.asm) is a
committed excerpt.

## MN10300 assembler (encoder)

The raw `.incbin` blocks can only become real re-assemblable source once we can
turn MN10300 assembly *back* into bytes. Since no GNU binutils MN10300 target is
available, [`tools/mn10300_asm.py`](tools/mn10300_asm.py) provides one — the
inverse of MAME's disassembler, in unidasm's operand syntax. Validated by
round-tripping every instruction of code region 1 against unidasm
(`tools/validate_asm.sh`):

```
MN10300 encoder round-trip over 588953 instructions:
  exact byte match : 588462 (99.9%)
  unsupported form : 419 (0.1%)
  byte mismatch    : 72 (0.01%)
```

The 419 unsupported lines are all one unidasm misprint, `fa 9x` stores to
`(d16, sp)` printed with a register like `d100`; the 72 mismatches are encodings
the compiler (or a hand-written routine) made longer than needed, where ours is
the shorter valid one. `tools/gen_program_s.py` repairs the misprint from the
opcode byte and spells the long forms explicitly: `call T:32` / `jmp T:32`, and
an immediate width `0x30:32` / `0x10:16` (or `udf00 0xec:16, d0`), so every
instruction of the program re-encodes byte-exactly. The encoder covers the
`udfNN`/`udfuNN` user-defined-function ops (the JPEG IDCT multiplies with
`udf00 imm16`), the `other*` register-list bits, the bit ops on `(aN)` and
`(d8, aN)` and `mov sp, (d8, aN)`. unidasm also swaps the registers of a
load `fc 00`..`fc 7f` from `(d32, aN)`; the generator rebuilds those from the opcode
byte too.

`make` regenerates the reference images by invoking the sibling extraction repo,
so the whole chain — original `.SLD` floppies → LZSS decompress → reassemble →
byte-compare — is reproducible from scratch. Override paths if your checkout
differs:

```
make EXTRACT_DIR=/path/to/kn7000_extraction DISKS_DIR=/path/to/KN7000 \
     UNIDASM=/path/to/mame/unidasm
```

## Toolchain

There is no free GNU binutils target for the MN10300 in common distros, so this
project ships its own minimal assembler, [`tools/kn7asm.py`](tools/kn7asm.py)
(pure Python, no dependencies). Its job is reconstruction, not full codegen: it
understands `.byte`/`.word`/`.long`/`.space`/`.align`, `.ascii`/`.asciz`,
labels/`.equ`/`.org`/`.mnbase`, `.include`, the two `.incbin` forms,
`.be16`/`.be24`/`.be32`, and `.macro`/`.endm` (positional or keyword arguments,
defaults, `\@`); expressions take `+ - * / % << >> & | ^ ~`. An
instruction operand may be `NAME+N`. A label may be used before it is defined;
the source is assembled again until every such use was right (`--labels FILE`
seeds the first pass with the previous build's addresses, so an unchanged
program takes one pass instead of five; when the seeded pass is not exact the
assembler starts again without it, because a stale seed can settle a branch in
its long relaxed form). `.incbin_range "file", START, END` asserts that the current
output offset equals `START`, so any gap or overlap in the region layout is
caught immediately.

For **new** code (homebrew apps) there is [`tools/xapasm.py`](tools/xapasm.py), a
two-pass assembler on the same encoder: labels are CPU addresses and may be used
before they are defined, and operands take expressions. Two companions build an
SP7001 SD-card app: [`tools/xap_addon.py`](tools/xap_addon.py) places a module in
the unused tail of the vendor `BASEEXT.XAP` and hooks `XapEntry` to it, and
[`tools/sd_splice.py`](tools/sd_splice.py) overwrites a same-size file in place on
a FAT SD-card image. The demos themselves live in the `kn5000_homebrew` repo
(`demos/kn7000_clock`).

Disassembly listings are produced by **MAME's `unidasm`**
(`unidasm <rom> -arch mn10300 -basepc <cpu_addr>`); `make disasm` drives it.
`disasm/program_entry.asm` (the boot/entry region) and
`disasm/table_directory.asm` are committed as curated samples; the full ~30 MB
linear listing is regenerable and git-ignored.

Some listings are **hand-annotated** rather than generated — currently
[`disasm/debugger_memdump.asm`](disasm/debugger_memdump.asm), the complete
semantic disassembly of the hidden factory MEMORY DUMP hex viewer (its chord
dispatcher, config-byte gate, all ten window-procedure event handlers, and its
static data). Those are not part of the byte-exact build, so
[`tools/verify_listing.py`](tools/verify_listing.py) (`make verify-listings`)
keeps them honest: it re-reads every byte column straight out of `baserom/` and
re-encodes every printed mnemonic with `tools/mn10300_asm.py`. Today it reports
2321 bytes verified with 0 mismatches, 0 unexplained gaps and 803/803
instructions re-encoding byte-identically.

Converted code in `src/program.s` itself can carry the same kind of
interpretation: [`annotations/*.ann`](annotations/README.md) give a converted
function semantic local labels (every branch inside it then names its target),
named data addresses, and header, block and end-of-line comments, all keyed by
CPU address and merged in by `tools/gen_program_s.py`. Since those functions are
part of the build, `make verify` checks them byte for byte, and `kn7asm` checks
each function label against its `.equ` in `src/symbols.inc`.

## Status

100% byte-match. **Code region 1 (file 0x80..0x186000) and the library image
(0x3B8FD1..0x3F6F01, run at 0x4C000000) are entirely MN10300 source**: 3,104
named and 33 unnamed region-1 functions and all 529 library functions, 670,646
instruction lines, no `.byte` escape. That is 1,853,232 of the image's 4,157,185
bytes (44.58%, `tools/coverage_score.py`; history in
[`notes/coverage-history.tsv`](notes/coverage-history.tsv)); what stays
`.incbin_range` is the data region 0x186000..0x3B8FD1, except the **display
palette** (256-entry `0x00BBGGRR` CLUT at `0x32573C`, typed `.long`).

The source is symbolic. Every function keeps its symbol-file name as a real
label (`kn7asm` checks it against its `.equ` in `src/symbols.inc`): the
reflection names of `kn7000.sym`, the hand-recovered names of
`kn7000_manual.sym` (which also give the library its function boundaries;
`LIB_CONVERT` in the generator only overrides an end). A function that can
also be reached through a pointer starts with a register-save prologue
(`movm [regs], (sp)` and/or `add -N, sp`) and is entered by `call` right after
it: its label is on the prologue and `X_entry` on the `call` entry (the
generator takes the pair only when every `call` of the entry saves the same
registers and opens the same frame; `notes/convert-probes/prologue_census.py`
counts them). A function no symbol file names yet is `func_<ADDR>`, its call
entry `func_<ADDR>_entry`; every branch target and every code address an
operand names is a label, `loc_<ADDR>` unless something names it. Data inside the code ranges is
typed rather than decoded (`DATA_ISLANDS`): the `.rodata` that code region 1
ends in (double-precision gain tables, a micro-ITRON `T_CTSK`) and the library
loader's copy descriptor at the end of the image. `notes/convert-probes/reach.py`
checks that nothing else decoded as code looks like data.

The functions read by hand before the full conversion carry their notes:
`FUNC_DOC` / `LIB_SECTION_DOC` in the generator and `annotations/*.ann` (labelled
listings, e.g. the BMP and draw helpers) -- among them the
**Techni-Chord harmony engine** (`TechniChordCompute`, the 14 per-style voicing
routines; parameter `0x8081` uses a legacy order that the GUI translates through
the 14-halfword table at `0x485EC940`, with `DUET 1` stored last), the
**control-panel serial protocol** (`PanelTransaction`/`PanelTxKick`, the ISRs
`PanelAtnIsr`/`PanelTxDoneIsr`/`PanelRxIsr`, the transfer machine
`PanelTxState1..6`/`PanelRxState8..9`, `PanelFrameDecode`,
`PanelButtonDispatch`; `kn7000_mame/notes/panel-serial-protocol.md`), and the
library's soft-float runtime and TG voice engine. Naming the `func_` functions
and the `loc_` labels is the next step: names go in the symbol files and
`make program-src` regenerates the source.
See [`kn7000_extraction/NOTES.md`](../../kn7000_extraction/NOTES.md) for the memory
map, region map and other findings that guide the work.

## SP7001 firmware (program 942 / table 83)

The KN7000's `sp7001` BIOS (Key Soft Service SD PLUG-iN) is a second byte-exact target, built
by reusing everything recovered for the default build rather than starting over. Program 942
is build 941 plus a few edits (all 2302 reflection names survive, shifted by +0/+2/-17 bytes),
so `tools/offset_map.py` maps every byte exactly and `tools/port_symbols.py` carries the names
across (2291 of 2302 at exactly the address 942's own tables give; 1622 of 1623 manual names).
`gen_program_s.py --profile sp7001` then ports 941's function split, data islands and notes:
3,143 named + 34 unnamed region-1 functions and all 538 library functions come out as MN10300
assembly (`src/sp7001/program.s` and its parts in `src/sp7001/program/`). What is new in 942 is a
**plug-in host** (validates and calls an 'XAPR' plug-in at table address `0x483E8000`) and a
**name-based export table** of 231 services for it (uITRON kernel calls, file and compression
APIs, buffer accessors) -- 228 names build 941 never had (`kn7000_sp7001_exports.sym`, pairing
verified against uITRON interrupt semantics). Table 83 is table 84 with 6 small segment changes
plus that plug-in appended, which `tools/gen_table_s.py` disassembles (its own 35 reflection
names; the activation gate named from the earlier reverse-engineering). That plug-in loads
`.XAP` extensions to the fixed RAM address `0x5029B000`; `BASEEXT.XAP`, from the SP7001 table
update, is disassembled too (`tools/gen_xap_s.py`), and the update's two table disks prove
table 83 byte-for-byte. Full measurements and
the edit-site catalogue: [`notes/sp7001-build-diff.md`](notes/sp7001-build-diff.md).

### Table build 80

Table 80 pairs with program 893 (v1.3): it is the table flash of Felipe's own instrument, read as two
EPROM halves (private romset, de-interleaved like SP7001's into `baserom/kn7000_table_b80.rom`, which
is not committed; SHA-1 `2e50a40b...`). It is table 83's first 0x3E0660 bytes (the 85-entry directory
and its 84 segments) with one byte different, the second digit of segment 07's build marker (`"80\n"`
against `"83\n"`, at 0x139EE9), and erased flash where table 83 has its plug-in.
[`src/b80/table.s`](src/b80/table.s) therefore holds no copy of table 83: it takes the bytes of the
table-83 build and spells out the one that differs. `make verify-table80`.

### Program builds 935 (v1.5) and 893 (v1.3)

Program 935, the release before 941, is a third byte-exact program target, made like 942 by
porting rather than re-deriving. Its reference is the EPROM pair of the private romset,
de-interleaved into `baserom/kn7000_program_b935.rom` (not committed; SHA-1 `5690195d...`).
Unlike 942 it is not 941 plus a few insertions: 941 rewrote and reordered the DSP boot code at
the front of code region 1 and moved blocks of the data region. So `gen_program_s.py --profile
b935` ports what the offset map places 1:1 and drops what it cannot. All 2302 reflection names
sit where 935's own tables put them, and 4420 of 941's 4426 symbol rows port. Two more names are
carried by code (`tools/port_names_by_code.py`). `tools/check_ported_names.py` finds 3609 of the
ported names on the same relocation-masked routine as in 941, and one on an edited routine. The
result is 3104 named + 33 unnamed region-1 functions and all 529 library functions as MN10300
assembly, with no `.byte` escape. `make verify-935`.

Program 893 is the program flash of Felipe's own instrument (the romset's halves are the
dumper's reads; it pairs with table 80). It is made the same way (`--profile b893`). 2206 of the
2298 reflection names in its own tables sit at the ported address. The other 92 take the
table's address: they name rewritten code or ambiguous runs. 4404 of the 4426 symbol rows port,
and 2 names are carried by code. 3550 of the ported names sit on the same routine as in 941 and
49 on an edited one (mostly SD-card handlers). The result is 3094 named + 33 unnamed region-1
functions and 527 library functions, with no `.byte` escape. `make verify-893`. Measurements,
method and what is left: [`notes/older-program-builds.md`](notes/older-program-builds.md).

## Style Convert Disk converters (.CNV)

DISK MENU > STYLE CONVERT runs loadable MN10300 programs from the Style Convert Disk:
`scd7000` and `scd6000` in MAME's floppy softlists. `src/cnv/` holds all of them, seven
programs. Five files are the same on both disks, and `TECHNICS.CNV` is two builds.
`make verify-cnv` rebuilds each one byte for byte. It takes the disk images from the softlist
set and checks them against the softlists' SHA-1 first.

They are **fully disassembled**: no `.incbin`, and no `.byte` in code. `tools/gen_cnv_s.py`
finds the code by recursive descent; the converters make no indirect call or jump. It then
decodes the routines nothing calls, until no gap is left. Every branch target is a label, every
call target a routine, and every address an operand names is a label. Strings, pointers and
data are typed by how the code reads them. The `.data` image is assembled at its run address
with `.mnbase`.

Routines with the same code in several converters are found together. 75 are common to all
seven: the mailbox and error routines, the C library, soft-float and byte-order helpers. A name
in `cnv_manual.sym` reaches every copy. Routines byte-identical to named PROGRAM 941 routines
take the firmware's names.

The file layout, the mailbox requests seen from the converter side, the error codes and the
per-file numbers are in [`notes/style-converter.md`](notes/style-converter.md).

## IC18, the boot ROM

The CPU starts at `0x40000000`, where IC18, the 4 MB rhythm ROM C3CBND000046, answers. Its first 64 KB are
the instrument's boot ROM: reset, the bus and cache set-up, and the **update system** the firmware cannot
provide for itself (it cannot rewrite its own flash). Held keys at power-on open the UPDATE SYSTEM MENU,
DEVICE INFO or UPDATE DISK CHECK; update floppies (`KN7KP1`..`KN7KA2`, an LZSS image after a kind and a
sum sector) or update files on the SD card (`KN7KPRG.DAT`..) are written into the program, table, IC21,
CS0 or picture flash; then it jumps to the firmware at `0x48400000`. [`src/ic18/boot.s`](src/ic18/boot.s)
is all of it, made by [`tools/gen_ic18_s.py`](tools/gen_ic18_s.py): recursive descent through its jump
tables, then every gap decoded; every routine named from the code (`kn7000_ic18.sym`) or from the
firmware where the code is the same, every table typed, nothing `.incbin`'d. The reference is cut from the
chip image in the private romset (SHA-1 checked, not committed). Details, including the rest of IC18 (the
rhythm data): [`notes/ic18-boot-rom.md`](notes/ic18-boot-rom.md). `make verify-ic18`.

## IC19, the picture ROM

`src/picture.s` rebuilds the 2 MB the CPU sees at `0x57800000` from the chip's own pictures:
a directory of 102 offsets, then the 100 PRESET pictures of the Slide Show, each a 640x240
JPEG in `src/picture/` brought in with `.incbin` and padded with `.align 4`. The read it
reproduces was made on a real KN7000 (PROGRAM 893) on 2026-10-19 with `tools/cnv_romdump`;
`make verify-picture` checks the rebuild against that read's SHA-1, and against the read
itself when it is at hand. Why only 2 MB of a 64 Mbit chip, how the firmware reads it, and
what the pictures are for: [`notes/ic19-picture-rom.md`](notes/ic19-picture-rom.md).

## Manual symbol supplement

`kn7000_manual.sym` hand-names functions that the firmware's own reflection
tables (which produce `kn7000.sym`) leave unnamed -- recovered by reverse-
engineering in the sibling `kn7000_mame` driver effort (panel serial protocol,
MIDI ISRs, button dispatch, tone-generator register writes; see that repo's
`notes/`). `make disasm` merges it with the generated `kn7000.sym`. It does not
affect the byte-exact build (`make verify` stays 100%).
