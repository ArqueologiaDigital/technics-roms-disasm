# The data region of program 941 as typed source: the MILK GUI first

Lane gui-kn7000 of the data-semantics effort (`notes/data-semantics-2026-10-29/README.md` at the
repository root), 2026-10-29.  Until this lane, program build 941's data region (file offsets
0x186000..0x3B8000, CPU 0x48586000..0x487B8000, plus the 0xFD1 bytes before the library image)
was three `.incbin_range` lines and a typed palette.  It is now `src/program/data/`, generated by
`tools/gen_data_s.py` and byte-identical (`make verify`).  Builds 942 (SP7001), 935 and 893 get the
same from the same generator (`--profile sp7001 / b935 / b893`, `src/<build>/program/data/`,
`make verify-sp7001 verify-935 verify-893`).

## What is where

| file                                | what it holds                                                                    |
|-------------------------------------|----------------------------------------------------------------------------------|
| `src/program/data/data.s`           | the region's top file: includes the constants, the two `.inc` files, the parts   |
| `src/program/data/data_NN.s`        | the region in address order: tables, records, strings, gaps                      |
| `src/program/data/gui_classes.inc`  | one assembler macro per MILK class that a record uses, plus CLASS / OBJ / IDNAME |
| `src/program/data/gui_ids.inc`      | the TT_ (title), MD_ (mode) and OTB_ (OT block) ids, each with its screen        |
| `src/program/data/labels.sym`       | every data label (address, name, item size), read by gen_program_s.py            |
| `src/program/data/media/`           | the 8 JPEG and 2 BMP files the region holds whole                                |
| `notes/gui-data-region/menu-map.md` | the generated menu map: every block, screen and widget, and the title index      |

Tools (all in `kn7000/tools/`, each with a docstring saying what question it answers):

| tool                 | question                                                                          | run                                   |
|----------------------|-----------------------------------------------------------------------------------|---------------------------------------|
| `milk_model.py`      | which bytes are MILK classes, tables and widget records, and what each field is   | `python3 tools/milk_model.py --check` |
| `gen_data_s.py`      | the data region as typed source                                                   | `make data-src`                       |
| `gui_menu_map.py`    | which screens exist, what is on them, which title / menu entry leads where        | `make gui-map`, `make verify-gui-map` |
| `gui_readability.py` | per program tree: records typed, ids / links / addresses still spelled as numbers | `python3 tools/gui_readability.py`    |

`kn7asm.py` gained what the typed source needs (shared with lanes kn7000-ic18 and kn7000-wave, one
implementation): `.macro` / `.endm` with defaults and keyword arguments, `\@`, and the operators
`/ % << >> & | ^ ~`.

## Format, with the evidence for each structure

### The registry

`RegisterObjectTable` (CPU 0x4842A717) copies a 16-byte `{u32 class, u32 proc, u16 count, u16 pad,
u32 table}` to `0x5011FAAC + 16 * slot`.  The program makes 400 such calls, 396 of them from the 36
`InitializeBlockNN` routines, 11 per block at slots `16*N + k`:

| k | class        | table holds                                                    |
|---|--------------|----------------------------------------------------------------|
| 0 | Viewable     | pointers to the block's widget records                         |
| 1 | Function     | code pointers (9: their names)                                 |
| 2 | ApFunction   | code pointers (10: their names)                                |
| 3 | MainFunction | code pointers (11: their names)                                |
| 4 | Class        | 24-byte class records                                          |
| 5 | Event        | pointers to EV_ names                                          |
| 6 | Method       | pointers to MT_ names                                          |
| 8 | ResName      | pointers to the widget records' names, index-parallel to k = 0 |

An id is `(slot << 16) | index`: class ids 0x0004KKKK, event ids 0x0005KKKK, method ids
0x0006KKKK, an object of block N is `(16N << 16) | index`, a function `((16N + k) << 16) | index`.
Evidence: ClassProc (0x4842A802) indexes the table of registry slot `id >> 16` with `id & 0xFFFF`
times 0x18; `ClassProc` itself sends method `0x00060025` (block 0 Method table entry 0x25).
`milk_model.parse_calls` finds the registrations by tracking the stores to the four stack words and
the slot in d0 before each call.

The same tracker reads `RegisterOTBlock` (0x484317D1: d0 = block, a0 = "OTB_" name, slot 0xC),
`RegisterTitle` (0x48431836: d0 = index, a0 = "TT_" name, stack +0x10 = the screen object's id,
+0x14 = the OT block; 0x1C-byte records at 0x50031C64, slot 0xF) and `RegisterMode` (0x484317EC:
d0 = index, a0 = "MD_" name, 0x10-byte records at 0x50031A64, slot 0xE): 36 OT blocks, 283 titles,
21 modes.  Their ids are `gui_ids.inc`.

### Classes

The 24-byte class record and its field names are the KN5000's (`scripts/analysis/
nakarest_objtab_map.py`, THE CLASS SYSTEM): proc +0, parent +4, u16 allsize +8, u16 selfsize +10,
name +12, propdata +16 (one type character per own field), propname +20 (pointers to the own
fields' names, the last an empty string).  518 classes in 36 tables.

What differs is the layout: the KN7000's compiler aligns.  A class's own fields form a C struct
(each field at a multiple of its size; the rect `P`, four s16, at a multiple of 2; padded to its
widest field), its size is `selfsize`, and it starts at the parent's `allsize` rounded up to its
alignment; `allsize` is the end rounded up to 4.  The byte size of each type character
(`milk_model.SIG_SIZE`) starts from the KN5000's table, with `f` = 1, `l` = `G` = `_` = 4 and
the new `E` = 4, `D` = 2.  `milk_model.py --check` asserts selfsize and allsize for all 518
classes, and every super / sub / next / prev link of the 8,509 records (next.prev and sub.super
are the record itself): 0 failures.  [INFERENCE] `D` could be 1 instead of 2: only two classes
use it and both pad to 8 either way.

### Widget records

A record is its class chain's fields, root first.  Viewable's: class +0 (the record's own class
id), super / sub / next / prev +4..+10 (indices in the same Viewable table, 0xFFFF none), flag
+12, rect +14 as {left, top, right, bottom}.  [INFERENCE] right and bottom are inclusive: the
full-screen Screen objects hold 0, 0, 639, 239 on the 640 x 240 LCD; the macros take X / Y / W / H
and store X + W - 1 and Y + H - 1.  The struct padding the macros write as `.space` is zero in all
8,509 records (`gen_data_s.check_pads`).

33 records, and every state variable a record points at (the `l` / `m` / `q` / `r` fields:
selected, onoff, window, parent, child, ...), are in the initialised work-RAM image that
ResetEntry (0x4840FF7E, loop at 0x48410068) copies from ROM 0x487B0B78 to RAM 0x50000010 (0x7F34
bytes).  That image is assembled under `.mnbase 0x4FC4F498`, so its labels are the RAM addresses
the code and records use.

How a field value is spelled (the type character is the class table's own):

| type            | fields (most common)                      | spelled as                                          |
|-----------------|-------------------------------------------|-----------------------------------------------------|
| `[`             | super sub next prev                       | object name (`<name>_ix`)                           |
| `P`             | rect                                      | `X=, Y=, W=, H=`                                    |
| `\`             | flag                                      | `VF_*` bits                                         |
| `]`             | color fontcolor ...                       | `CL_*`                                              |
| `^`             | border                                    | `BD_*`                                              |
| `e`             | editsw editsw2                            | `ES_*` (the soft-key the widget answers)            |
| `X`             | str caption title stron stroff            | string label, the text in the line's comment        |
| `a`             | exit title titleNowN ...                  | `TT_*` title id                                     |
| `` ` ``         | mode                                      | `MD_*` mode id                                      |
| `s` `N`         | window screen                             | `<object>_id`                                       |
| `j` `k`         | func main_func                            | `FN_*` function id                                  |
| `l` `m` `q` `r` | selected onoff window parent ...          | label of the RAM state variable, `<object>_<field>` |
| others          | index, length, font, icon, bmp, align ... | decimal                                             |

The `CL_ BD_ ES_ VF_` names are the firmware's own name / value tables (`src/constants.inc`,
`tools/gen_constants.py`).

### Object names

A record whose ResName is not empty (2,200 of 8,509) is named by it.  The others are named
`<nearest named ancestor>_<class without its Vw/Ac/Ps/Iv prefix>` plus the label text when the
record shows one, numbered when that repeats.  These generated names are the source's; the
firmware has none for those objects.

## Readability census (`tools/gui_readability.py`)

Before: the baseline checkout at b58b8f696 (`--root` of the main checkout); after: this branch.

| tree        | records typed | records in blobs | raw ids | numeric links | numeric addresses | code -> data nums | unnamed fields |
|-------------|---------------|------------------|---------|---------------|-------------------|-------------------|----------------|
| before, 941 | 0             | 8509             | 0       | 0             | 0                 | 12433             | 0              |
| after, 941  | 8509          | 0                | 359     | 0             | 6                 | 12433             | 0              |

The 359 raw ids left are values of id fields that no registration names (mostly function ids of
blocks whose Function tables are empty, and the `0x00020000` default procedure); the 6 numeric
addresses are pointers into data the generator did not type.  "code -> data nums" counts the
converted code's immediates that are data-region addresses spelled as numbers: the code is
generated by gen_program_s.py, and naming them there is the next step (see Open questions).

## Open questions and what remains

- The code names data addresses by label now: gen_data_s.py writes `labels.sym` beside the data
  (address, name, item size) and gen_program_s.py spells every 8-digit immediate that is a data label,
  or lies inside a typed item, as `Label` / `Label+N`.  The two generators read each other's output,
  so `make data-and-code-src` (`tools/regen_data_and_code.sh`) runs them alternately for all four
  builds until no labels.sym changes: three rounds on 2026-10-29.  GUI ids in the code (`mov 0x00060025, d1` =
  a method id, object ids, title ids) are still numbers: naming them is the next step.
- About half of the data region's bytes are still `.incbin_range` (see the lane report for the
  list): the built-in style / rhythm data (big-endian records like IC18's, around 0x486D0000 and
  0x48729988), tables the code indexes with computed offsets (0x485BC3EC: a 69 KB run of code
  pointers and signed byte tables), and mostly-0xFF sparse tables.
- 30 zlib streams are declared opaque: they inflate (MIDI-like event data, "Soloist Sounds"
  name data, 2,272-byte `ZZZZ` records) and Python's zlib at level 6 re-compresses every one
  byte-exactly, so typing their inflated payloads and compressing at build time is possible; the
  inflated bytes are not committed because that would put bulk dump bytes in git.
- [INFERENCE] the rect's right / bottom are inclusive (from the full-screen objects only).
- `D` (IvSDPlayTimer / IvSDFwdRewTimer) may be 1 byte rather than 2.
- The object names this source gives the 6,309 objects with an empty ResName are invented
  (parent + class + text); they are stable across regenerations only while the tree is.

## Website page draft

(For `kn7000-gui-objects.md` in technics-docs, to be added by the website sync.)

> **The KN7000's screens in the source.**  The KN7000 firmware draws every screen from data: 8,509
> widget records in 36 blocks, each an instance of one of 518 MILK classes that the firmware
> describes itself (name, parent, size, and a name and type for every field).  In the disassembly
> each record is now one line, named by its class:
>
>     Screen   PanelSimulator, sub=PanelSimulator_ExitMode1, flag=VF_Const, X=0, Y=0, W=640, H=240,
>              color=CL_Green, border=BD_Double1, exit=TT_PS, window=PanelSimulator_window
>       AcTitleMenu  PanelSimulator_TitleMenu_DEBUG_TOOLS, super=PanelSimulator, ..., X=327, Y=200,
>              W=305, H=38, str=Str_DEBUG_TOOLS, title=TT_DEBUG      # str "DEBUG TOOLS"
>
> The indentation is the widget tree; links are object names; `title=TT_DEBUG` is the title the
> entry opens, and the title list (`gui_ids.inc`) says which screen each title shows.  The menu map
> (`kn7000/notes/gui-data-region/menu-map.md`) is generated from that source: all blocks, all
> screens and the title index.  The layout rules (aligned C structs, unlike the KN5000's packed
> ones), the registry slots and the id scheme are in `kn7000/notes/gui-data-region/README.md`.
