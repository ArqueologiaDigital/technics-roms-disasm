# The SX-KN7000 wave ROMs: format and source, 2026-10-29

The four 16 MiB wave ROMs now have byte-exact sources, `src/wave/main.s` and `src/wave/sub.s`. They are
checked by `make verify-wave`, which is part of `make gate-kn7000`. Each source describes one tone
generator's stream, laid out like this:

- the directory, as typed `.word` fields with symbolic pointers;
- the parameter records, as `.word` lists spelled with named flags;
- the recordings, one labelled `.incbin` each of a raw item made from the recording's WAV file
  (since 2026-10-30, `../../notes/media-files-2026-10-30/README.md`; until then an `.incbin_range` of
  the git-ignored reference stream, declared `census: opaque -- pcm`). Since 2026-11-02 an item is cut
  where its recording ends: an explicit loop's 32-sample run-out is a line of its own, `<label>_RunOut`,
  read from the loop's first samples, and zero words up to the next recording are `.space` (below,
  "Where a recording ends");
- the erased fill at the end of a page, as `.space`.

The data census row `kn7000-wave` read 3,682 opaque PCM items (66,319,584 bytes) and 0 generic; since
2026-10-30 those 3,682 items are `generated` from their WAV files (the "from media" column). The rest
of the 64 MiB is typed: 789,280 bytes of directories, records, alignment and fill.

Probes: `wave-roms-probes/` (README there). The read port and the service test are in `wave-rom-port.md`.

## Layout of a stream

A stream is 16 pages of 0x100000 words, 2 MiB each. A page is 1 MiB of each chip. Each page is
self-contained:

```
page word 0        directory: N entries of 4 words (A, P, B, Q)
          4N       parameter records, one per entry, in entry order, each 32-bit aligned (pad 0)
          ...      zero fill to the next 16-word boundary
          16*B0    recordings (PCM), each starting on a 16-word boundary, in B order
          ...      0xFFFF fill to the page end
```

`layout_probe.py` checks these rules on all 32 pages and all 3,974 entries. Every one holds:

| rule | what it checks                                                                       | holds for      |
|------|--------------------------------------------------------------------------------------|----------------|
| R1   | entry 0's A = 4 x N                                                                  | 32 of 32 pages |
| R2   | records follow the directory in entry order, on even words, pad words 0              | 3,974 of 3,974 |
| R3   | the first recording is at the first 16-word boundary after the records; the gap is 0 | 32 of 32       |
| R4   | there is no 0xFFFF run of 128 words or more inside a page (fill is only at the end)  | 32 of 32       |
| R5   | P bits 15:12 = 1                                                                     | 3,974 of 3,974 |
| R6   | record word 0 = the entry's B                                                        | 3,974 of 3,974 |
| R7   | Q = the record's first parameter word                                                | 3,974 of 3,974 |
| R8   | the code field is non-zero only in the records of 8-bit entries                      | 3,974 of 3,974 |

`tools/gen_wave_s.py` re-checks R2, R3, R5, R6 and R7 while it writes the source, and stops if one fails.

The recording at a page's highest B runs to the end fill. The source starts the fill at the first
16-word boundary inside the trailing 0xFFFF run, because a recording's own last samples may be -1. The
end-fill columns below are the raw run, so a few of them are a little longer than the `.space` in the
source. The directory gives only starts; where each recording ends follows from its record (below,
"Where a recording ends"). No recording runs into the next one, but 101 starts (125 entries) are not
recordings of their own: they are alternate starts into an earlier recording.

### Directory entry

| word | name | meaning                                                                        | evidence                                                                                                   |
|------|------|--------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------|
| 4j   | A    | the entry's record, in words from the page start                               | R1, R2 (`layout_probe.py`)                                                                                 |
| 4j+1 | P    | `0x1000 \| R<<9 \| E<<4 \| F<<3 \| K`                                          | see the rows below                                                                                         |
|      | R    | bit 9 (`PREV`): the entry plays a recording backwards (one entry, below)       | `wave_reverse_entry.py`; [INFERENCE] from its sound name, B and record                                     |
|      | E    | bits 8:4, pitch exponent: a period of 2^(E-9) samples sounds at the note       | inference from emulation: kn7000_mame `notes/g13-waves-2026-10-20/pitchcheck.py`, 478 of 556 traced voices |
|      | F    | bit 3 (`PCM8`): two signed 8-bit samples per word, low byte first              | `format_probe.py`: 929 of 937 recordings with F set read better as 8-bit; 4 of 2,721 with F clear do       |
|      | K    | bits 2:0 (`GRAN_16` .. `GRAN_2048`): segment and loop granule L = 2^(K+4)      | `loop_probe.py`: with this L, 945 of 954 marked loops repeat; with L/2 or 2L, 1 of 1,887                   |
|      | -    | bit 12 (`PFMT`): set in every entry; bits 15:13 and 11:10 clear in every entry | R5; meaning BLOCKED (see the open questions)                                                               |
| 4j+2 | B    | the recording's first sample, in units of 16 words (32 bytes) from the page    | R3, R6; with this unit the probes find the loops                                                           |
| 4j+3 | Q    | a copy of the record's first parameter word                                    | R7                                                                                                         |

E ranges over 13 to 19, so it fits bits 8:4. Bits 11:10 are clear in every entry, and bit 9 is set in
one: main page 0x00 entry `0x0AF`, `P = 0x12fa` = `PFMT | PREV | 15<<4 | PCM8 | GRAN_64`, the value of
its neighbours (E 15, 8-bit, `GRAN_64`) with bit 9 added. It is the **Reverse Cymbal**, and bit 9 is
read here as "play backwards" (`wave_reverse_entry.py`; the meaning of the bit is an [INFERENCE], the
facts below are measured):

- **Its sound.** Parameter record 658 selects it for keys 12-96. Its bank key (MSB 0, LSB 0x78,
  program 110) is used by the archive records " Reverse Cymbal ", "Reverse Cymbal *", "ReverseCymbal",
  "Reverse Cym.1" and "Reverse Cym.2". Entry `0x0AE`, its neighbour, is selected by record 636 (LSB
  0x08, program 110): "Ride Cymbal 1" / "Ride Cymbal 2" (and IC307 calls the same audio
  `RideCymbal2`).
- **Its B is not a recording of its own.** The 10,944 words from B (word 0x28b00) to the next start
  read as 16-bit audio (lag-1 correlation 0.989, as 8-bit 0.006), not as the 8-bit samples P bit 3
  asks for. They are the middle of entry `0x065`'s 16-bit recording, inside its loop (words
  0x26f80..0x2b580, whose run-out repeats the loop start).
- **Its B is a negated address.** -B mod 2^16 = 0xd750, the last 16-word unit of the 30,848 8-bit
  samples (964 units, 0xd38d..0xd750) that entry `0x0AE`'s segments cover. Units -(B + n) mod 2^16,
  n = 0 .. 963, are exactly `0x0AE`'s units from its last down to its first.
- **The same segments.** Both records lay out 128, 128, 54, 128 and 44 granules of 64 samples.
  `0x0AE` puts LOOP_START and LOOP_END on them; `0x0AF` has no loop and ends with a `REC_END` word,
  whose one granule (below) falls on the two units below `0x0AE`'s first, 0xd38b..0xd38c, which are
  zero: the reversed cymbal ends in silence.

So the tone generator, given bit 9, reads the address counter negated and plays `Main_P00_W0AE`
backwards, from its end. The source spells it that way: E0AF's B is `0x10000 - ((Main_P00_W0AE -
Main_P00) / 32 + 963)` and the stream has no `Main_P00_W0AF` item; the 21,888 bytes that used to be
one are the rest of `Main_P00_W065`. The firmware never reads P (`wave_port_readers.py`), so the chip's
own behaviour is not observed; a listening test of the Reverse Cymbal would confirm it.

### Parameter record

The record at A is B again, then parameter words `[flags:2][code:6][value:8]`, up to the first word
with bit 15 set:

| value / flags                                | meaning                                                                        | evidence                                      |
|----------------------------------------------|--------------------------------------------------------------------------------|-----------------------------------------------|
| value >= 0x80                                | a segment of (256 - value) granules, laid out from the first sample            | `loop_probe.py`                               |
| flag `LOOP_START` (0x4000) on a segment      | the loop starts at the segment's end                                           | `loop_probe.py`                               |
| flag `LOOP_END` (0x8000) on a segment        | the loop ends at the segment's end, and so does the record                     | `loop_probe.py`; the record grammar           |
| `LOOP_END` with no `LOOP_START` before it    | the loop starts at the recording's first sample                                | `wave_record_extent.py`: 20 of 20 run-outs    |
| value < 0x80, descending multiples of 8      | the "split list": ONE granule each, after the segments                         | `wave_record_extent.py`, `wave_split_list.py` |
| `REC_END` (0xc000), value 0 or a split value | ends a record that has no LOOP_END; also one granule                           | `wave_record_extent.py`                       |
| code, bits 13:8                              | non-zero only in 8-bit entries; in emulation it scales the segment by 2^(-b/2) | R8; g13 `code8fit.py` (a fit, not derived)    |

So every word of a record is a run of granules: a value of 0x80 or more is (256 - value) of them, any
other value exactly one.

Record shapes, over all 3,974 entries (S = segment, k = split value, Z = value 0, digit = flags):

- `Z3`: no data words, only `REC_END`. Main 988, sub 66.
- `S*1S*2`: an explicit loop. Main 577, sub 377. These are the 954 entries `loop_probe.py` tests.
- `S*k*Z3`: main 338, sub 397.
- `S*Z3`: main 263, sub 410.
- `S*k*3`, where the last split value carries `REC_END`: main 239, sub 295.
- `S*2`: main 18, sub 2.
- Rare: `S*k*ZZ3` main 2; `k*3` 1 in each.

Without an explicit loop, the emulation model loops the single granule after the last segment (g13
README). For `S*Z3` that granule is the record's last one; for `S*k*` records it is the first split
granule, and the model never plays the rest. The data say otherwise: the record runs on through every
split granule to the `REC_END` word's (below). What the chip does after a record's last granule is not
verified on hardware.

### Where a recording ends

`wave_record_extent.py` takes each record's extent from the grammar above:

- **with LOOP_END:** the loop end plus the 32-sample run-out that repeats the loop's first samples;
- **without LOOP_END:** the sum of the granules of all its words, the `REC_END` word's included.

Measured over all 32 pages (Main_P00_E0AF left out, it has no recording of its own):

| what                                                                   | MAIN       | SUB        |
|------------------------------------------------------------------------|------------|------------|
| recordings                                                             | 2,178      | 1,402      |
| alternate starts: entries whose start lies inside an earlier recording | 96         | 29         |
| ... that end exactly where that recording ends                         | 96         | 29         |
| recordings with nothing between their end and the next recording       | 2,125      | 1,376      |
| recordings followed by a run of zero words (16 to 224 words)           | 53         | 26         |
| recordings followed by any non-zero word before the next one           | 0          | 0          |
| recordings whose extent runs past the next recording's start           | 0          | 0          |
| "segments, then REC_END" records whose last granule is all zero        | 187 of 262 | 296 of 410 |
| split-list records whose last granule is all zero                      | 0 of 432   | 0 of 564   |

So the record gives every recording's exact end, and there is no separate "pad": recordings with an
explicit loop end 32 samples after it, the others on their last granule, and the few gaps between
recordings are whole 16-word units of zeros. An **alternate start** is a second entry into one
recording: entries 0x064 and 0x065 of main page 0x00 both play one 16-bit bell recording, 0x064 from
its first sample (the sounds "Bell Piano", "Shining E.P.", "Glimmer"), 0x065 from 19,456 samples in
("Bell Pad", "Bell Line", "Fantasia", "Digi Stack"), with the same loop and the same end (main 96 entries, all with their recording's
loop; sub 29). The WAV files were cut at every distinct start, so such a recording is spread over two
or three WAV files; the source says so in the item's comment ("an alternate start into ...'s
recording").

## How the firmware selects a recording

The voice's shadow register word `+0x40` carries a 20-bit select. Bits 19:12 are the page and bits 11:0
the directory entry. Two library routines of program 941 build it. The library is linked for
`0x4C000000`; its source is `src/program/library_01.s`.

- **The entry.** `TgElemNoteOnStd` (`0x4C030A98`) reads the tone-zone descriptor at `*(librec+0x34)`. It
  does `movhu (2, a0), d0; and 0x0fff, d0` and ORs the result into `+0x40` under the mask `0xfffff000`.
  `kn7000_manual.sym` records that `TgElemNoteOnFresh` (`0x4C033CAE`), the fresh-strike programmer,
  calls the same routing routine (`0x4C037C1B`). Its entry-field store was not traced here.
- **The page.** `TgVoiceRouteFieldSet` (`0x4C037C16`) takes the low byte of the descriptor's halfword
  `+0`. It does `and 0xff; asl 12` and stores the result into bits 19:12 of `+0x40` (mask
  `0xfff00fff`). Its mode argument changes the page:
  - Mode 0 asks the hardware subtype (`PanelSubTypeGet_entry`).
  - Subtypes 1 and 2 use the page as it is. Felipe's unit reads strap `0xF8F7`, which is subtype 2.
  - Subtype 3 maps it through the halfword table `0x485877B4`: pages 0x00-0x07 to 0x20-0x27, and
    0x08-0x0F to 0x30-0x37.
  - Subtype 5 maps it through `0x48587774`: 0x00-0x03 and 0x08-0x0B to 0x20-0x23, and 0x04-0x07 and
    0x0C-0x0F to 0x28-0x2B.
  - Modes 1 to 4 add 0x20 or 0x30, the expansion board's pages.

  The tables were read from `baserom/kn7000_program.rom`.
- **Measured in emulation.** The shadow word reaches the tone generator as register plane 0x1C. In the
  kn7000_mame trace `strap1` (g13 README), all 556 traced voice note-ons name an internal page and an
  existing entry. 478 of them pass a pitch check made with E. The emulator was wrong about one thing: it
  reported subtype 5, under which every select was remapped to an expansion page.

So select 0x0A00F names `Main_P0A_E00F` on the MAIN tone generator and `Sub_P0A_E00F` on the SUB one.
On Felipe's firmware (893), the piano's C4 used selects 0x0A00F and 0x08023, one on each TG; the g13
README does not record which TG took which. No CPU
reads these ROMs except the service-mode checksum (`wave-rom-port.md`). The tone generator reads the
directory and the records itself.

## The source

| file                       | what it is                                                                                                |
|----------------------------|-----------------------------------------------------------------------------------------------------------|
| `src/wave/wave_format.inc` | the field constants (`PFMT`, `PREV`, `PCM8`, `GRAN_*`, `LOOP_START`, `LOOP_END`, `REC_END`) with evidence |
| `src/wave/main.s`          | the MAIN stream: per page `Main_PNN`, entries `Main_PNN_EJJJ`, records `_RJJJ`, recordings `_WJJJ`        |
| `src/wave/sub.s`           | the SUB stream, the same way (`Sub_PNN_...`)                                                              |
| `tools/gen_wave_s.py`      | wrote the two sources from the reference streams, checking the layout rules (`make wave-src`)             |
| `tools/wave_pair.py`       | chips to stream (`join`) and back (`split`), whole-buffer slicing                                         |

- **Labels.** A recording is named after the lowest entry that plays it. Its census reason gives the
  sample count, the format and every entry that plays it, for example
  `; census: opaque -- pcm: 1024 16-bit samples, entry 001`.
- **Directory lines.** One entry looks like this:

  ```
  Main_P00_E003:	.word	(Main_P00_R003 - Main_P00) / 2, PFMT | 18<<4 | GRAN_512, (Main_P00_W003 - Main_P00) / 32, 256-2
  ```

- **Recording lines** (2026-11-02). A recording that ends inside its item is cut there. An explicit
  loop's run-out is `<label>_RunOut`, an `.incbin` of the loop's first 32 samples: main 490 and sub
  359 of them, the 20 loops with no LOOP_START included (they read the recording's first samples). The
  6 + 3 run-outs that are not an exact copy (`loop_probe.py`) are read from their own place. Zero words
  before the next recording are
  `.space N, 0`. The WAV files still hold the whole item, run-out and zeros included, so the cut changes
  no medium; the build reads the same raw items. An alternate start keeps its own WAV file, and its
  comment names the recording it belongs to.
- **Assembler change.** For this, `tools/kn7asm.py` expressions gained `/` (integer division), `<<`,
  `>>`, `|` and `&`, with Python's precedence.
- **Speed.** `kn7asm.py` now reads each `.incbin` file once per run instead of once per directive. An
  `open()` on the virtiofs share costs about 3 ms, and `main.s` alone has 2,251 `.incbin_range` lines,
  read on each of two passes: 28 s before, 2.7 s after. Every other kn7000 target still rebuilds
  byte-identically (`make gate-kn7000`, 2026-10-29).

## Open questions

- **The page order: answered 2026-11-02** (`wave-roms-probes/wave_page_order.py`). The firmware's tone
  database fixes it. All 5,215 zones of the 'JK' archive (`table-semantics-2026-10-29.md`) name a
  (page, entry) on one TG, and a page can only sit where every entry its zones name exists. Of the 16!
  orders, that leaves one for MAIN (the dump's) and two for SUB: the dump's and the swap of pages 0x0B
  and 0x0E, which both hold 36 entries. The pitch decides between those two: over the 47 neighbouring
  zone pairs that touch them, a sound's log2(period), E - 9 + corr/3072, rises by more than half an
  octave going up the keyboard in 0 pairs as dumped and in 10 with the pages swapped. A permutation of
  32 KB banks *inside* a page is unlikely, though this is an inference: R1-R4 hold in all 32 pages, and
  `loop_probe.py` finds 945 of 954 loops exact, comparing samples up to a page apart.
- **The split list: what it is, answered 2026-11-02; what the value does, BLOCKED.**
  (`wave-roms-probes/wave_record_extent.py`, `wave_split_list.py`.) Each value below 0x80 is one more
  granule of the recording, after the segments, and the record's last word (`REC_END`) is one more: with
  that, every record covers its recording to the last sample. 1,181 of 1,273 lists descend by exactly 8
  per granule. Neighbouring split granules are nearly the same waveform (median correlation 0.994), the
  slow end of a sustained or decaying sound. The value follows the pitch: of 452 pairs of entries that
  play one recording with different lists, every pair differs by a constant, the higher list always
  belongs to the higher keys, and the constant is 8 per octave (8 for 11.2 keys apart on average, 16 for
  24.3, 24 for 37.2, up to 48 for 74.7). So a value is a per-granule quantity in steps of 1/8 octave of
  playback pitch, set per zone so that the result is the same at every pitch [INFERENCE: a time, e.g. how
  long the granule lasts, would need exactly that]. No firmware code reads it (`wave_port_readers.py`:
  only the service checksum touches the wave-ROM latches), and no TG register write carries it: the TG
  reads it from the record. What the chip does with it needs the TG's datasheet, or a line-out recording
  of one split-list sound (e.g. "60s E.Piano", main page 0x00 entries 0x047-0x053) played an octave
  apart, whose tail length would show whether the granules are timed.
- **P bit 12, always set: BLOCKED** (TG datasheet). Bits 15:12 read 1 in all 3,974 entries and bits
  11:10 are clear in all of them. No firmware code reads P (`wave_port_readers.py`), so no register write
  shows what the chip does with it. No other dumped stream could vary it: KN5000 IC307 is a Y chip and
  holds no P word, and the KN6000 / KN6500 wave ROMs are not dumped (`technics_romsets/kn6000` and
  `kn6500` hold placeholders only).
- **The 8-bit gain law: BLOCKED** (2026-10-31, `../../notes/sound-2026-10-31/README.md`, section 2). The code
  field's meaning, `2^(-(code&7)/2)`, is a fit (g13 `code8fit.py`). The high three bits of the code are
  unexplained, and so is the code on `REC_END` words. No firmware reads it, no TG datasheet is known, and none of
  548 searchable 8-bit recordings has a 16-bit copy to measure against. A line-out recording of an 8-bit sound
  on the owner's unit would settle it.
- **Sample rates: answered 2026-10-31** (`../../notes/sound-2026-10-31/README.md`, section 1). Each WAV header
  carries the TG's read rate at the recording's root key, from `src/wave/root_rates.tsv`
  (`tools/wave_root_rates.py`: the pitch law, E, the zone correction and the key maps). A zone's side bit
  0x400 is the MAIN TG and 0x800 the SUB one (658 of 658 single-TG zones), which settles "which TG, MAIN or
  SUB, each side bit means" in `table-semantics-2026-10-29.md`.
- **What plays after the loop: answered 2026-11-02** (`wave-roms-probes/wave_record_extent.py`). No
  release segment: after an explicit loop the stream holds only the 32-sample run-out, then the next
  recording or whole units of zeros (MAIN 496, SUB 362 such recordings; no non-zero word). The "data past
  the loop" seen before was of two kinds. In records without LOOP_END it is the split list's granules,
  which the record itself lays out (the emulation model looped the first of them and dropped the rest).
  In items cut at an alternate start it is the rest of a recording that another entry also plays. The
  firmware sends nothing at key-off that could pick a release segment: `TgVoiceEgBurstWrite`
  (`0x4C0376DE`) writes the release halves of registers 0, 1, 4, 5, 8 and 9 and `TgVoiceGateOff`
  (`0x4C0376A0`) register 3 and class 0x3000, no select (the select, plane 0x1C, is written at note-on);
  the only release *sound* is `TgKeyOffSample` (`0x4C03656E`), a new note-on with its own recording for
  some drum-kit zones. Still unverified on hardware: what the chip does after a record's last granule
  without LOOP_END. In one-shots that granule is digital silence (MAIN 187 of 262, SUB 296 of 410
  "segments, then REC_END" records); in split-list records it never is, which fits a chip that loops the
  last granule [INFERENCE].
- **Recording boundaries: answered 2026-11-02** (above, "Where a recording ends"). The record gives every
  recording's end; the source cuts each item there (`<label>_RunOut`, `.space`). The WAV files are not cut:
  they still end at the next start, run-out and zeros included, and the 101 alternate starts keep a WAV
  of their own. Merging those (one WAV per recording, with its alternate starts as cue points) and trimming
  the run-outs would change about 100 and 850 WAV files: an owner decision, not done.
- **The odd entry `Main_P00_E0AF`: answered 2026-11-02** (above): the Reverse Cymbal, bit 9 = play
  backwards [INFERENCE], E = 15. Its old item `Main_P00_W0AF` (21,888 "8-bit samples") was 16-bit audio
  of `Main_P00_W065`; the WAV files `Main_P00_W065.wav` and `Main_P00_W0AF.wav` are replaced by one.
- **A static cross-check: answered 2026-10-31** (`table-semantics-2026-10-29.md`, lane mn10300-rest): all
  3,753 zones of the 864 zone lists and all 1,462 of `JkKitZones` name an existing wave entry on the TG
  their side bits pick.
- **Shared recordings with the KN5000: answered 2026-10-30.** The g13 README inferred that KN5000 IC307
  is the Y half of such a pair. It is: 1,342 of IC307's 1,413 waves occur verbatim in the KN7000's Y
  chips (1,162 in IC203, 180 in IC207, none in an X chip), 1,339 of them at the first sample of a
  KN7000 recording, and IC307's 256-word test sine is exactly the even samples of `Main_P00_W000`
  (`../../notes/media-files-probes/ic307_kn7000_match.py`, `pcm_encoding_probe.py`). No 1 MiB page
  of IC307 equals a page of a KN7000 chip because the pages hold different selections and orders.
  `src/wave/ic307_names.tsv` names 1,241 KN7000 recordings after the IC307 wave with the same audio.

## Website page draft

> ### KN7000 wave ROMs
>
> **The chips.** The SX-KN7000 has two tone generators. The MAIN TG at `0x98050000` reads IC203 and
> IC204, and the SUB TG at `0x98040000` reads IC207 and IC208. Each chip is a 128-Mbit (16 MiB) mask
> ROM. A tone generator's two chips are one stream of 16-bit samples, low byte first: word i of the Y
> chip (IC203, IC207), then word i of the X chip (IC204, IC208). The chip fetches two neighbouring
> samples at once.
>
> **Pages.** The stream is 16 pages of 2 MiB. Each page starts with a directory of 8-byte entries:
>
> | field | meaning                                                                                                |
> |-------|--------------------------------------------------------------------------------------------------------|
> | A     | the entry's parameter record, in words from the page (entry 0's A = 4 x entry count)                   |
> | P     | `0x1000 \| R<<9 \| E<<4 \| F<<3 \| K`: reverse R, pitch exponent E, 8-bit flag F, loop granule 2^(K+4) |
> | B     | the first sample, in 32-byte units from the page                                                       |
> | Q     | a copy of the record's first parameter word                                                            |
>
> **Records.** A record is B, then words `[flags:2][code:6][value:8]`:
>
> - every word is a run of granules: a value of 0x80 or more is a segment of (256 - value) granules,
>   any other value one granule;
> - flag 0x4000 marks the loop start at a segment's end, and 0x8000 the loop end (without a loop start,
>   the loop starts at the first sample); 32 samples after the loop end repeat its first 32;
> - values below 0x80 form a split list, one granule each, descending by 8: a per-granule value in
>   steps of 1/8 octave of pitch, which entries playing one recording at higher keys raise by 8 per
>   octave; what the chip does with it is not known;
> - 0xc000 ends a record that has no loop end; its word is one more granule.
>
> So the record gives every recording's exact end. **Recordings.** They follow the records, each
> starting on a 32-byte boundary; each page ends in 0xFFFF fill. The main pair holds 2,426 entries and
> 2,178 recordings, the sub pair 1,548 entries and 1,402 recordings; 125 entries start part-way into a
> recording that another entry plays from its start.
>
> **One entry plays backwards.** Main page 0x00 entry 0x0AF, the Reverse Cymbal, sets P bit 9; its B is
> the negated address of the last 16-word unit of the ride cymbal recording of entry 0x0AE, which it
> plays from the end.
>
> **Page order.** The tone database's 5,215 zones fix the order of the 16 pages of each stream: only the
> dumped order lets every zone name an existing entry and keeps each sound's pitch falling smoothly
> across its zones.
>
> **How the firmware picks one.** It names a recording by a 20-bit select written into the voice's
> register `+0x40`: bits 19:12 the page, bits 11:0 the entry (`TgVoiceRouteFieldSet`, `TgElemNoteOnStd`
> in the program's library image). The tone generator reads the directory, the records and the samples
> itself.
>
> **Byte-exact source.** The disassembly rebuilds all four chips byte for byte from
> `kn7000/src/wave/main.s` and `sub.s` (`make verify-wave`).
