## What was fixed today

1. **The `--jobs N` hang (2026-11-17 issue 1): found and fixed** (117dd396c).  The build's marker check
   (`cc900_firmware_c.check_markers`, reached through `label_map` / `module_names` before `finish()`) stops with
   `sys.exit` on a wrapped `cc900-name:` marker.  `run_job` caught only `Exception`; `SystemExit` is not one, so it
   ended the pool worker.  `multiprocessing.Pool` replaces a worker that exits but loses its task, and
   `imap_unordered` then waited for that result for ever.  The hung recheck's log held exactly two such exits, and
   the two processes found hung were the replacement workers (forked later, from a parent that by then had threads).
   Now `run_job` catches `SystemExit` too (the listing is reported as not read, its rows kept), and `execute()` uses
   `concurrent.futures.ProcessPoolExecutor`, which raises `BrokenProcessPool` when a worker dies instead of hanging.
   Checked: three runs indexed with `--jobs 1`, the old pool and the new executor give byte-identical output
   (`probes/README.md`); the recheck that hung ran to the end with `--jobs 2` (three listings not read, each a C file
   with a wrapped marker).  `--jobs 2` is safe again.
2. **`--recheck --update` rewrote rows it had not selected.**  It updated every row of each re-read listing, but
   the other functions of a listing were translated from whatever C `source_c()` found for the selected rows (the
   near-miss copies of those rows only, when the corpus is gone), and rows were matched by (listing, function), so
   the variants of one label collided.  The first recheck of today, committed as d84256090, turned 99 MATCH rows
   into NEAR this way (`probes/status_moves.py 117dd396c d84256090`).  Fixed: only the selected rows are updated,
   paired by `pair_rows()` (by name, else by order).  The index was rebuilt from the pre-recheck state 117dd396c:
   `--add-new` for the new runs, then the recheck of every error status with the fixed code.
3. **Variants of one label are compared** (were ERR-dup, not compared): a probe file that maps several C functions
   to one label with `cc900-name:` now gets every variant linked and compared on its own.  New index column
   `listing_name` tells them apart (empty in rows from before today; `pair_rows` pairs those by order).  Checked with
   `probes/first_occ.py`: the first variant's results do not move.
4. **Names the attempt's own C does not resolve** (its C was not found, or the copy found lacks the line) are looked
   up in the `cc900-name:` lines and long names of the C main's trees build (`main_c_maps`, only one-way names):
   ERR-resolve / ERR-name rows like `.Voice_PerVoice_PortaPitchUpd` or an ambiguous 31-character cut that main's C
   writes in full.  It cannot make a false MATCH (the bytes are still compared with the ROM), but a row that MATCHes
   this way may have a C copy without the `cc900-name:` line: add it before staging.
5. **`why` for ERR-asm** (was empty): llvm-mc's / ld.lld's error message and the refused line's mnemonic only.
6. **`why` for ERR-translate no longer holds listing text.**  It used to carry the refused listing line itself
   (`cp A,QE`-like fragments; they are in the index of the commits before today, which cannot be rewritten).  Now
   only its shape: the mnemonic, register names, `sym` for any other name and `N` for any number.
7. **ready.tsv**: the `in_lane_worktree` column is now `c_elsewhere`: the src-root's cc900-staged/, a lane worktree
   (committed or not), or a local branch main has not merged (`branch:<name>`); `none` when the C copy in `c/` is
   the only C for the function anywhere.

## Open

- **Translator gaps behind ERR-translate / ERR-asm** (for whoever owns `model/to_llvm.py`; not changed here): a
  byte register llvm-mc names only by its extended code as the SECOND operand of `cp` / `or` / `add` (`cp A,QE`,
  `cp C,QE`, `cp A,IXL`, `or A,QIZL`, `add L,QIZH`: `erp_byte()` handles them as the first operand only, 66
  attempts).  ERR-asm (122) now says why: a translated line that starts with a literal backslash-t (`\tnop`, 54
  attempts: some translator path writes the escape itself), an absolute address computed past 24 bits
  (`0x10003c223`, 29: a negative offset added as unsigned), and operands llvm-mc refuses for `or` / `ldw` / `sll`.
- **ERR-resolve that only the lanes' branches can resolve**: today's sub-CPU floating-point runs call `._fld_fl` /
  `._fld_dl` / `.memcpy`, whose runtime names are in lane_sub's branch (`scripts/build/cc900_runtime_names.tsv`),
  not on main.  After that merge, `--recheck --status ERR-resolve --update` resolves them.
- **ERR-data**: functions with an f_const object and no `cc900-data:` line (a C-side fix, as before).
- **The three unread listings** (wrapped `cc900-name:` markers in old HD C) keep their 2026-11-17 rows.
- Issues 6 and 7 of the 2026-11-17 handoff (class heuristics, `name+funcs` provenance) are unchanged.

    cd <worktree of cc900/nearmiss, merged with main>
    nice -n 10 python3 -B scripts/analysis/cc900/nearmiss.py --add-new --jobs 2
    # after main gains translator / runtime-name fixes:
    nice -n 10 python3 -B scripts/analysis/cc900/nearmiss.py --recheck \
        --status ERR-translate,ERR-data,ERR-asm,ERR-resolve,ERR-name,ERR-dup --update --jobs 2

minutes for 20-25 runs with `--jobs 2`; the full error recheck about 20 minutes.
