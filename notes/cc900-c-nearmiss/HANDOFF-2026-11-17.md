## Open issues

1. **The error rows were NOT rechecked against main's latest translator.**  After main gained fdatas, the
   (XWA+QIZ) forms and `jp (reg)` (merged into this branch at 5b2943bc2), the recheck of the error rows hung.
   Command: `nice -n 10 python3 -B scripts/analysis/cc900/nearmiss.py --recheck --all --status
   ERR-translate,ERR-data,ERR-asm,ERR-resolve --update --jobs 2`, started 2026-11-17 about 00:20 UTC.  At about
   01:50 UTC the coordinator found it had run 91 minutes on about 2 minutes of CPU: parent pid 1952800, workers
   1953717 and 1954143, one worker in `pipe_read`, the other in a futex wait, neither with a child process.  Their
   temp folders had not changed since 01:14, and each held only the `c.c` it had just written.  This looks like a
   `multiprocessing` deadlock in `execute()`'s pool, not slow work.  It was stopped (no index row was written:
   `--update` writes only at the end, and `git status` was clean).  The final refresh then ran with `--jobs 1`,
   which uses no pool, and finished in 463 s.  The rows added by that refresh were translated with the current
   translator; the older error rows were not.  To recheck them later, use one process:

       nice -n 10 python3 -B scripts/analysis/cc900/nearmiss.py --recheck --all \
           --status ERR-translate,ERR-data,ERR-asm,ERR-resolve --update --jobs 1

   Before going back to a pool, find the deadlock.  Suspects: `derive_module()` keeps a per-process objdump of a
   whole image in `MODIMG` (large pickles of the job dicts, whose `ctext` and `_job` travel back through the result
   pipe), and the pool forks a process that has already run subprocesses.
2. **Unresolved names (ERR-resolve, 435 attempts):** callee names V4.23 cut to 31 characters that match no single
   tree label (`.Voice_Build_GateCommand_NoParti`, `.Voice_Pitch_WriteOutReg_Sec`); string-literal labels
   (`_SingleLoad_LoadPanelMemory_Str_`, `_ExtData_ToneParam_MultiChannel_`); condition codes looked up as names
   (`eq`, `ne`: a `to_llvm` gap); `._findfirst`.  The `why` column has each one.
3. **ERR-dup (236):** two listing functions resolve to one tree label, mostly HD probe files that define the same
   function under two names.  The second is not compared.
4. **ERR-data (110):** functions with an f_const object (switch table, FP constant) and no `cc900-data:` line;
   the build refuses them, so the index does too.
5. **`cc900-name:` markers that wrap.**  During the hung recheck the build warned twice that a `cc900-name:` marker
   in a lane's C is not whole on its line; the build reads each marker from one line only.  The final refresh
   printed no such warning.
6. **The class rules are heuristics** (the script's docstring defines them); "other" is what they cannot explain,
   and the ROM size of a non-matching function is found by following its branches, so "length-only" can mean that
   estimate overshot.
7. **Provenance.**  Runs whose corpus directory no longer reproduces the run's corpus.tar SHA-256 are matched by
   file name and function set (`name+funcs`), likely but not proven; `runs.tsv` says which.

## Resuming the hourly refresh

    cd <worktree of cc900/nearmiss, merged with main>
    nice -n 10 python3 -B scripts/analysis/cc900/nearmiss.py --add-new --jobs 1

`--add-new` indexes only the runs `runs.tsv` lacks and appends them; it rewrites `README.md` and `ready.tsv`.  Use
`--jobs 1` until the pool deadlock (issue 1) is understood.  It needs the main checkout's `rebuilt_ROMs/*.elf`
(for the `cc900-module:` lines) and the private oracle at `~/compartilhado/cc900-oracle`.  Commit `notes/
cc900-c-nearmiss/` after each pass, with the commit message in a file (`git commit -F`).

Other commands: `--recheck` (re-translate stored listings, no VM), `--ready` (`ready.tsv` from the index),
`--readme` (`README.md` from the index), `--explain LISTING FUNCTION` (one alignment, for the terminal only).
