# Phase 3b design: the LLVM implementation of the reference model (2026-11-10, for approval)

Phase 3a built a Python reference model of cc900 (`scripts/analysis/cc900/model/`, state at 2026-11-10 02:00: micro
corpus 674 / 674 exact at all four option sets, 1997 library 185 / 248, 223 firmware pairs byte-identical through
our own llvm-mc, semcheck 1 DIFFERENT, reviewed).  `PLAN.md` 3.2 and `phase0.md` 4 say the LLVM implementation
follows the model.  This note inventories the model, chooses the architecture from that inventory, and stages the
work.  Nothing in the fork is touched by it; the owner approves before any LLVM code is written.

**Recommendation in one line.**  Build 3b as the plan's *fallback* (b): a C++ port of the model that reads clang's
AST and emits through our MC layer, selected by `-mcc900-compat=`; keep (c), the Python model through `llvm-mc`, as
the interim product for phase 6 and as the differential oracle of the port; drop (a), IR plus metadata, because the
inventory shows that most of the model's decisions read syntax that LLVM IR does not carry.

**Why (b).**  Section 1.2 shows that the decisions worth having (the four allocators, the templates, evaluation
order, the frame) read the syntax tree.  Design (a) can only get it by serialising the AST into metadata and
re-reading it after clang's IRGen has already normalised the code; at that point IR is a lossy transport of the
AST and LLVM's selector and allocator contribute nothing the model uses (its allocators are fitted priority lists,
its selection is a template per node, its frame is planned before code is written).  Design (b) hands the port the
same tree the model reads, in the same process, with the right types, and leaves clang's IR path untouched, which is
what the gate requires.  One consequence: the port cannot live in `llvm/lib/Target/TLCS900/` (LLVM may not depend on
clang), so the plan's `TLCS900CC900*.cpp` become `clang/lib/CodeGen/CC900/CC900*.cpp`; only two small MC changes go
into the target.  The function attributes of PLAN 3.1 (`"tlcs900-cc900"`...) are left unused: there is no IR to carry
them.

**Why keep (c).**  It works now (223 pairs, `tiny.c` 6 / 6) and the model is where the rules are still being
fitted daily.  Phase 6's build rule can use it today (the owner decides, question Q3), and it is the differential
oracle for every stage below: the port must reproduce the model's lines, not only the oracle's.

**What (b) costs that (c) does not.**  Two implementations of every rule while the model keeps moving.  The
mitigation is the staging: a module is ported once its ledger rows have been stable, the port's listing dump is
compared with the model's lines on the whole corpus after every change, and the Python model stays the fitting tool
(question Q4 asks whether that remains so after parity).

## 3. The staged plan for (b)

Common to every stage:
- **Own files** under `clang/lib/CodeGen/CC900/` (library `clangCC900`), one per model module, with the model's
  function names kept so that a reader can put the two side by side.  The internal representation is the model's
  **line list** in Toshiba mnemonics (`CC900Line`): the line passes and the comparison instruments port one to one,
  and `CC900Emit` (from `to_llvm.py`) lowers lines to `MCInst` at the end.
- **The gate:** `-mcc900-compat` selects a separate `ASTConsumer` (`CC900Action`), so clang's IR path is not entered;
  the default-mode tests (105 TLCS900 CodeGen + MC lit tests, the `tlcs900-cc900*` clang tests, `make gate`,
  `make gate-wsa1`, the 104 `v10/maincpu` C files byte-identical, phase 2's harness) must pass unchanged at every
  stage.
- **Instruments:** (1) `-mcc900-listing` (cc1 only) dumps the port's lines in the model's normalised format, so
  `score.py` and `listing.py` compare them with the oracle's listings and with the model's lines unchanged;
  (2) `port_check.py` (new, beside `score.py`) runs both on a corpus and reports every function whose lines differ:
  **the differential must be 100 %** on the stage's corpus, misses included; (3) bytes: the port's object against
  `llvm-mc` on `to_llvm.py`'s translation of the model's lines, and against the oracle's asm900 objects with
  relocations masked (as `lib_match.py` does); (4) `pairs_llvm.py` (`pairs_model.py` with the port in the model's
  place) and `semcheck.py` on the port's listing dump.  Scores are quoted from these scripts and committed in
  `results/model_ledger.md` as a second column.
- **Tests in the fork:** `clang/test/CodeGen/tlcs900-cc900-compat/<stage>-*.c`, small hand-written files with
  FileCheck lines in our syntax, one per rule family, our C and our expectations (no oracle text, D1); the whole
  corpus runs from the disasm repository.  MC changes get `llvm/test/MC/TLCS900/` tests.

Calibrated combinations today: `-mcc900-opt=0` without `-mcc900-size` (the oracle's `none`, `Xr`) and
`-mcc900-opt=3 -mcc900-size` (`O3XS`, `O3XSXr`).  The firmware used `-O2` / `-O3` with `-XS`.  Any other
combination is unmeasured; question Q6 asks what the flag should do with it.

Personalities and rules.  The model's `PERSONALITIES` map resolves `ide2003` and `v1.10` to `kn5000`: on the corpus
the two dev-kit compilers differ from that rule set in no rule the model has yet.  The only live switch is the
reload rule; the other rows of `rules.md` are V4.23 behaviours that `kn5000` keeps, so they need no switch until
phase 7 builds the by-products.

In the port a personality is a `CC900Personality` record of booleans, one per row, with the four presets; a rule
is tested by name at the point where the model tests `F.personality`, so a fifth personality or a decided rule is
a table row, not code.
