# Step I0: the compiler passes we hold

Made by `python3 -B notes/cc900-feedback-plan-2026-11-22/i0_inventory.py` (static reading of the PE headers only;
nothing was run).  Its output follows the findings.

## Findings

- **Three builds of each pass, fourteen copies.**  thc1 is the parser and thc2 the code generator (their banners say
  so; the 2003 thc1's banner is formatted differently).  The other kits hold copies: sebastianmihai.com's are the
  1998 files, franck.charlet's are the 2009 ones, and each installer's two languages (1033 / 1041) share one file.
- **Stripped.**  No debug directory and no COFF symbols in any of the six: function names must be recovered.
- **Linked with Microsoft Visual C++**, linker 5.10 (1998), 6.00 (2003) and 8.00 (2009), with the C runtime linked
  statically (each imports only KERNEL32).  So a decompiler's MSVC runtime signatures can set the library apart
  from Toshiba's code.
- **The size of the job.**  V4.23's code generator is 270,464 bytes of code (`.text`); it grew to 303,294 in 2003
  and 428,378 in 2009.  Its function count is not known before I1 (the frame and `ret` byte counts are upper bounds,
  and the 1998 build often omits frame pointers).
- **Tooling for I1.**  The machine has only binutils' `objdump`: no Java, no Ghidra, no capstone, no pefile.  A
  decompiler matters here (the allocator's decisions are easier to describe from decompiled control flow than from
  linear disassembly), so I1 installs Ghidra with a JDK under `~/compartilhado/tools/` and runs it headless; its
  projects go in the private `cc900-oracle/internals/`.
